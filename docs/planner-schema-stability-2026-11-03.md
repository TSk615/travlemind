> 当前上线代码：`c4c524a`。仅替换 API 与 Worker，使用完成下述验收的同一镜像；网页、搜索、数据库和 Redis 未替换，没有执行数据库迁移。

> 本文记录一次具体故障的修复范围和有限验收结果，不代表模型、网络或第三方来源永远不会失败。先前版本的一次真实生成成功，并不足以证明生成链路稳定；后续公开账户仍发生了结构校验失败。

## 这次故障是什么

公开任务 `job_1bbc1e18fdcc6624c24b` 在 **2026 年 11 月 3 日 13:45–13:50（北京时间）**失败。后台记录表明：初次完整行程与一次格式修复均返回了 JSON，但没有通过行程数据模型校验，最终报 `schema_validation_failed`。

旧代码只保留了这个笼统错误码，没有保留具体字段路径和校验类型；被拒绝的原始模型文本也没有保存在检查点中。因此不能追溯断言原任务究竟是哪一个字段出错，更不能归咎于某一个搜索供应商。使用相同输入重新调用模型曾通过结构检查，说明单次重跑成功无法排除随机失败。

## 修复内容

1. **完整行程也使用严格结构化输出**：初次规划和完整结构修复，都从当前运行的 `LlmPlanningPayload` 生成 JSON Schema，通过现有 Responses / Chat Completions 协议发送；不再只要求“输出一个 JSON 对象”。
2. **以运行时模型为准**：用真实 Schema 替换历史手写输出示例，避免示例与实际字段、枚举、可空类型和嵌套结构不一致。局部修复继续沿用原有的最小字段权限 Schema，不扩大修改范围。
3. **修复有具体目标**：校验错误保留字段路径和错误类型，例如 `days[0].items[0].schedule_intent.purpose / literal_error`；限制最多 20 项，不保存字段值、原始响应、供应商凭据或完整自定义异常消息。正常用户仍只看到中文阶段和安全提示。
4. **证据与输出分离**：`operation_evidence` 和 `railway_snapshot` 这类原始证据字典不交给规划模型自行填写；研究输入中的来源证据不删减，后续证据与可执行性校验不关闭。
5. **不靠放宽校验或无限重试掩盖错误**：仍保留独立的格式/内容修复预算、重复景点检查、时间与交通约束，以及最终失败的幂等退次。

## 连续真实验收发现的另外两类问题

第二版候选共完成 3 次真实全链路尝试，结果为 **1 次成功、2 次失败**，因此没有发布：

- `job_88ef77939569fa058a70`：结构正确，但多个硬冲突相互关联。局部补丁延长接驳，却未协调后续项目，并漏修重复 POI。
- `job_524d1ac62736d698cd6c`：活动时间表未发生结构错误，但修复后的可选留白仍与活动或旧留白重叠。

最终候选增加两种有边界的修复协议，仍只用原来的 **1 次语义修复**：

- **关联日期修复**：出现真实活动时间冲突，或至少 3 个非依赖、非单字段的硬冲突锚点需要共同处理时，允许模型协调这些授权日期内的安排；输出必须包含全部授权日期。服务器原样保留其他日期，并锁定已有城际交通的名称、起止时间、跨日偏移与原始证据。最终完整性校验仍必须通过。
- **真实空闲区间标注**：仅留白出错时，从固定活动时间表计算真实空闲区间，包含前一天跨夜交通的占用。模型只能给这些现成区间选择用途和备注，或明确不标注；不能自行写时间、插入景点或改动活动，旧的冲突标注整体替换。校验没有关闭，也不把重叠窗口当成正常留白保存。

在最终冻结镜像上，对这两份失败检查点各调用真实模型修复 **1 次**，均通过完整校验。关联案例只修改第 1、2、4 天，第 3、5 天保持不变；留白案例的全部活动保持不变。

### 混合分支也必须覆盖

第三版候选的 3 次全链路尝试为 **2 次成功、1 次失败**，同样未上线。失败任务 `job_5bdd625ee778e6fad788` 同时有接驳最短耗时不足和多个日期留白重叠；只测“单独修项目”与“单独修留白”不足以覆盖这个组合。

第四版冻结候选把两类权限分开：该案例只允许重排第 2 天，第 1、3 天仅按真实空闲区间修标注、全部活动保持不变。重排日期的 `flexible_windows` 明确输出 `[]`，自由时间可以留空并在当日摘要或备注解释，不另外编写一套可能冲突的时钟。其余局部修复分支同样不在改动活动/账本的同时再生成不可靠的留白时钟；这不删除景点，不放宽活动重叠、交通耗时、费用或来源的校验。

第四版对上述三份失败检查点各用 **1 次真实语义修复**，三份均通过最终校验。修复次数上限没有增加。
