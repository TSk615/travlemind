# TravelMind AI 项目阶段性总结（截至 2026-03-21）

## 1. 项目概述

TravelMind AI 是一个围绕“旅行规划闭环”构建的 MVP 项目，目标不是一次性做完所有旅游产品能力，而是先把最核心、最可验证的一条链路跑通：

- 用户注册/登录
- 创建 Trip（旅行 Brief）
- 触发行程生成（Generate）
- 查看生成结果与任务进度
- 进行 refine（二次调整）
- 搜索与整理结构化信息
- 导出 PDF

从当前代码落地情况看，项目已经形成了一个比较完整的全栈 monorepo：

- 前端：Vue 3 + Vite + TypeScript + Pinia + Vue Router
- 后端：FastAPI + SQLAlchemy
- 异步任务：ARQ + Redis（同时保留 inline 模式用于本地开发与测试）
- 数据层：当前测试与本地环境大量使用 SQLite；架构上兼容 PostgreSQL
- 共享类型：`packages/shared-types`
- Worker：独立 `apps/worker`

项目的关键设计原则是：

1. **先跑通闭环，再扩展能力**
2. **AI 编排与业务域解耦**
3. **前后端 API 合同稳定优先**
4. **本地 fallback 与真实模型路径并存**
5. **异步任务必须可观测、可追踪、可测试**

## 3. 目前项目中最值得讲的技术亮点

## 3.1 把 AI 功能做成“可替换适配层”而不是硬编码依赖

项目并没有让业务层直接耦合某个 Agent/模型实现，而是通过 orchestrator 边界进行隔离。

这样做的好处：

- fallback 可以稳定跑测试
- helloagents PoC 可以被封装在内部
- 后续切真实 LLM 服务时不需要推翻业务 API
- 产品合同和底层实现解耦

这在面试里可以总结为：

> 我们把“AI 能力”当成基础设施依赖，而不是把业务直接写死到某个 SDK 上。

## 3.2 把异步任务做成“可观测状态机”

很多项目只做到：

- 提交任务
- 等结果

而这个项目已经做到：

- 有 job 状态
- 有阶段语义
- 有阶段消息
- 有进度百分比
- 有 timeline 历史
- SSE 与普通 detail 返回结构一致

这非常适合用来回答面试中的系统设计问题。

项目没有强迫所有环境都依赖 Redis + Worker 才能开发，而是同时支持：

- `inline` 模式：本地自包含、测试稳定

这体现的是非常现实的工程取舍：

- 本地体验不能太重

## 4. 项目遇到的难点

下面这些是非常适合在面试里重点展开的“难点 + 解决方案”。

## 4.1 难点一：异步任务的一致性问题

### 难点表现

同一个 job 可能经历多个执行环境：

- API inline 执行
- Worker 异步执行
- 前端轮询查询
- SSE 实时流式订阅

如果状态更新不严谨，就会出现：

- job 卡在 queued
- 重复消费同一个 job
- SSE 和 detail 返回不一致
- 前端无法正确收敛状态

### 解决思路

项目最终采用了：

- 明确的状态流转：`queued -> running -> completed/failed`
- SQL claim 机制，避免同一 job 被重复执行
- `timeline_json` 保存每次状态推进历史
- SSE 与 detail 共用同一份 job 序列化结构

### 面试可讲点

> 难点不只是“异步”，而是“多个入口读写同一状态时，怎样保证一致性和幂等性”。

---

## 4.2 难点二：前后端契约需要稳定，但需求又在演进

### 难点表现

项目在推进过程中新增了：

- refine
- stage/progress/timeline
- settings/LLM 状态
- 更丰富的搜索字段

如果直接改接口而不控制兼容性，很容易导致：

- 前端报错
- shared types 失效
- 已有测试失效
- 页面和 API 合同错位

### 解决思路

- 使用 `packages/shared-types` 统一前后端类型语义
- SSE 与 detail 保持同结构，避免维护两套前端消费逻辑
- 在不改变主 envelope 的前提下增量加字段
- 新功能优先复用现有 job 体系，而不是额外起炉灶

### 面试可讲点

> 我们把“加功能”变成“在稳定契约上做增量演进”，而不是每次新增需求都推翻原来的接口。

---

## 4.3 难点三：如何兼顾真实模型与 fallback 稳定性

### 难点表现

产品既要能展示“将来能接真实模型”，又要保证：

- 本地开发不依赖外部 LLM
- 测试结果稳定可重复
- 配置缺失时前端也能解释当前行为

### 解决思路

- 使用 stub/fallback 作为默认稳定路径
- 通过 settings API 管理真实模型配置
- 前端通过 `LlmStatusNotice` 明确告诉用户当前走真实模型还是 fallback
- 创建 -> 生成流程不强行自动化，避免配置不完整时体验不可控

### 面试可讲点

> 我们没有把“真实模型接入”做成单点依赖，而是把它设计成一条可启用、可回退、可观测的路径。

---

## 4.4 难点四：SQLite 本地测试与字段演进兼容

### 难点表现

当 `JobRecord` 增加了：

- `stage`
- `stage_message`
- `progress_percent`
- `timeline_json`

如果本地 SQLite 库还是旧表结构，就会出现测试或运行失败。

### 解决思路

- 在初始化 / 查询 job 时增加 schema 兼容处理
- 对旧 `job_records` 表做自动补列
- 保持当前 SQLite 方案可继续工作，而不要求开发时立刻引入完整 migration 流程

### 面试可讲点

> 这类问题本质是“轻量环境如何跟上 schema 演进”，我做法是先保证开发与测试自愈，再为后续正式 migration 留出口。

---

## 4.5 难点五：产品路径清晰度问题

### 难点表现

用户创建完 trip 后，不一定理解：

- trip 是否已经自动生成
- 是否需要再点 Generate
- 没配模型时会发生什么
- 已经没有 itinerary 时为什么还能导出

### 解决思路

- 明确“创建只保存 Brief”
- 详情页新增“下一步 Generate”引导
- 已配置/未配置模型时给出不同提示
- Export 没有 itinerary 时直接禁用

### 面试可讲点

> 很多 bug 不是代码层面的，而是用户心智模型和系统真实行为不一致。我这轮专门修了这种“产品流程 bug”。

## 5. 出现过的 bug 与修复总结

下面这些是非常适合在面试里举例的真实工程问题。

## 5.1 Bug：ARQ 模式入队失败后 job 长时间停留在 queued

### 现象

当 Redis 不可用或 ARQ 入队失败时，任务虽然实际上不会执行，但 job 仍然停留在 `queued`，前端会一直轮询，看起来像“系统卡住了”。

### 原因

原先的入队逻辑在异常时没有把失败状态显式写回数据库，导致用户看到的是一个“永远等待”的假状态。

### 修复

- 在 ARQ 入队异常时，把 job 直接标记为 `failed`
- 同时写入 `error_message`
- 保证 `/jobs/{id}` 和 `/jobs/{id}/stream` 都能及时收敛到终态

### 结果

- 不再出现 job 无意义地卡在 queued
- SSE 能正确推送失败终态
- 前端可以给出明确错误提示

---

## 5.2 Bug：同一个 job 存在重复消费风险

### 现象

当 inline 与 worker 环境并存时，理论上可能出现一个 job 被执行两次。

### 原因

如果 job 只是“被读出来然后执行”，而不是先通过数据库原子 claim，就会有并发重复执行的窗口。

### 修复

- 使用数据库层面的状态 claim
- 只有 `queued -> running` 成功转换的一方才可以继续执行
- 其他执行方直接返回

### 结果

- 避免重复生成 itinerary
- 避免重复导出 PDF
- 提高 job 幂等性

---

## 5.3 Bug：SSE 与普通 job detail 返回结构不一致

### 现象

前端一边轮询 `/jobs/{id}`，一边监听 `/jobs/{id}/stream` 时，字段结构和终态判断不完全一致，会导致额外兼容逻辑。

### 原因

SSE 如果单独拼结构，很容易和普通详情接口渐渐漂移。

### 修复

- SSE 直接复用 job detail 的序列化结果
- 只额外加 `meta: { stream: true }`

### 结果

- 前端消费逻辑统一
- 降低维护成本
- 更适合后续继续加字段

---

## 5.4 Bug：PDF 导出的 URL、路径、返回结构不稳定

### 现象

导出完成后，可能出现：

- 前端拿到的 `file_url` 无法访问
- `file_path` 和实际静态挂载路径不一致
- 结果字段不足，难以复用

### 原因

导出逻辑、静态挂载路径、前端跳转路径之间没有完全对齐。

### 修复

- 修正导出目录解析
- 统一静态访问路径
- 返回稳定的 `file_name / file_path / file_url`
- 补充 `content_type / size_bytes`

### 结果

- 导出页可直接打开文件
- Trip 详情页可直接下载 PDF
- 导出结果更可观测

---

## 5.5 Bug：worker 注册函数名与 API 入队函数名不一致

### 现象

API 端 enqueue 的函数名和 worker 实际注册的处理函数不一致时，任务进了 Redis 也无法被 worker 正常消费。

### 原因

worker 入口和 API 入队字符串是分散维护的，容易命名漂移。

### 修复

- 对齐 enqueue job name 和 worker settings 中的 function name
- 启动时初始化数据库，保证 worker 端环境可直接复用 API handler

### 结果

- ARQ 模式链路更稳
- worker 能复用 API 侧 job 处理逻辑

---

## 5.6 Bug：新增 job 进度字段后，旧 SQLite 表结构不兼容

### 现象

增加 `stage`、`progress_percent` 等字段后，旧本地数据库直接报错。

### 原因

测试与本地开发使用的是已有 SQLite 文件，不会自动拥有新列。

### 修复

- 在 job 读取/初始化时增加自动补列逻辑
- 让当前 SQLite 环境继续兼容运行

### 结果

- 不需要手工删库重建
- 本地测试更加稳定

---

## 5.7 Bug：Trip 创建后用户不知道下一步该做什么

### 现象

创建完 trip 后，用户虽然到了详情页，但不确定：

- 系统是否已经自动开始生成
- 下一步是否需要点击 Generate
- 为什么还没有 itinerary

### 原因

产品流程没有把“创建 Brief”和“启动生成任务”明确拆开表达。

### 修复

- New Trip 页增加明确文案：创建只保存 Brief
- 详情页增加“下一步生成”信息面板
- 明确告诉用户 Generate 是进入攻略生成链路的动作

### 结果

- 用户流程更清晰
- 减少误操作和困惑
- 联调体验更顺

---

## 5.8 Bug：未生成 itinerary 时 Export 仍可点击

### 现象

用户可能在没有 itinerary 的情况下点击导出，触发无效请求。

### 原因

前端按钮启用状态没有和业务前置条件对齐。

### 修复

- 前端仅在已有 itinerary 时允许点击 Export

### 结果

- 避免无意义请求
- 减少失败提示噪音
- 流程更符合用户预期

---

## 5.9 Bug：shared-types 与前端新增设置页之间发生类型漂移

### 现象

前端构建时报错：缺少 `LlmSettings` / `LlmSettingsInput`。

### 原因

设置页与 store 已经依赖这些类型，但共享类型包没有及时补齐导出。

### 修复

- 在 `packages/shared-types` 中补上 `LlmSettings` 与 `LlmSettingsInput`
- 重新跑 `vue-tsc --noEmit`

### 结果

- 前端类型检查恢复通过
- 共享合同重新对齐

---

## 5.10 Bug：pytest 在 Windows 环境下临时目录权限异常

### 现象

pytest 在默认临时目录清理阶段容易出现 `WinError 5`，导致测试流程受环境影响。

### 原因

Windows + 当前沙箱/目录权限组合下，pytest 的临时目录清理逻辑容易失败。

### 修复

## 7. 还缺什么，才能做到“真正一键创建并生成”

目前系统设计上，`create trip` 和 `generate trip` 是明确分成两步的。

这符合当前后端契约，也降低了配置缺失时的不可控性。

如果要做到真正的一键创建并生成，还需要：

1. 后端提供原子化 create+generate 契约，例如：
   - `POST /trips?auto_generate=true`
   - 或单独 `POST /trips/create-and-generate`
2. 接口返回同时包含：
   - `trip`
   - `job_id`
3. 前端在创建成功后直接接管 job 轮询
4. 对真实模型、fallback、错误回退路径做更强的用户提示与重试策略

也就是说，当前系统已经把“创建后明确进入生成链路”的体验做顺了，但还没有在后端契约层做“一键化合并”。

## 10. 如果面试官追问：你修过最有代表性的 bug 是什么？

你可以优先讲这三个：

### 例子 1：ARQ 入队失败导致任务卡住

> Redis 不可用时，任务会永远停留在 queued，用户一直看到“处理中”。我修复成了：一旦 enqueue 失败，job 立刻转为 failed，并通过 detail 和 SSE 同步返回错误信息。

### 例子 2：创建 trip 后用户不知道下一步

> 这是一个产品流程 bug，不是代码报错。用户以为创建完就开始生成了，但实际并没有。我做的修复是：创建页明确提示“只保存 Brief”，详情页给出“下一步 Generate”的显式入口，并补上真实模型 / fallback 的运行提示。

### 例子 3：shared types 漂移导致前端类型检查失败

> 这是典型的多人协作问题。设置页和 store 已经用了 `LlmSettings`，但共享类型包没同步导出。我补齐 shared types 后，前端静态类型检查恢复通过。

## 11. 当前项目的不足与下一步规划

虽然闭环已经跑通，但项目还存在一些明显可继续提升的地方：

### 11.1 工程层面

- 前端完整 build 在当前环境下受 `esbuild spawn EPERM` 影响，需要在 CI 或标准开发机进一步验证

### 11.2 产品层面

- 还没有真正的一键 create+generate 契约
- 酒店、评分、广告识别还主要是接口预留 / 占位阶段
- 搜索源目前仍以 seed/manual/官方页为主

### 11.3 AI 层面

- 真实模型路径已经具备 settings 能力，但仍需进一步扩大真实生成逻辑的覆盖面
- fallback 很稳定，但还需要更多真实模型场景测试与 prompt 策略优化
